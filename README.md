# Lab 5: коллекции и generics

## Запуск

Из папки `Lab 5`:

```
javac -d out $(find src -name "*.java")
java -cp out task01.Main
```

Вместо `task01` подставить `task02` … `task15`. Общие классы (`CourseCode`, `CourseId`, `Course`) лежат в `src/model`.

## Ответы

### Задание 1. List и порядок
Список хранит порядок добавления. `list.remove(obj)` удаляет только первое совпадение, `list.remove(index)` удаляет по позиции.
Дубликаты ищутся одним проходом с `HashSet`: `seen.add(x)` вернул `false` — значит, дубликат. Это O(n), вложенные циклы дали бы O(n²).

Замер (50 000 элементов, лучшее из 5 запусков, микросекунды; цифры от запуска к запуску меняются):

| Операция | ArrayList | LinkedList |
|---|---|---|
| `get(i)` × 2000 | ≈ 100 | ≈ 50 000 |
| обход целиком | ≈ 600 | ≈ 700 |

Вывод: для чтения по индексу `ArrayList` лучше (O(1) против O(n) у `LinkedList`, разница в сотни раз). Для обхода разницы практически нет.
Это грубое измерение с прогревом через повторы, а не микробенчмарк (для него нужен JMH). Оно показывает порядок величин, а не точные числа.

### Задание 2. Set и уникальность
`LinkedHashSet` убирает дубликаты и сохраняет порядок первого появления. `HashSet` порядок не гарантирует, `TreeSet` сортирует.
`HashSet` и `LinkedHashSet` находят дубликат так: сначала сравнивают `hashCode`, затем `equals`. Если `equals/hashCode` не переопределены,
используются адреса объектов, и два «одинаковых» кода считаются разными (пример `BadCode` в выводе). `record` генерирует оба метода по всем полям.
Правило: равные по `equals` объекты обязаны иметь одинаковый `hashCode`.

### Задание 3. Map и индекс
Повторный ID ловится через `putIfAbsent`: он возвращает прежнее значение, если ключ уже был. По результату бросается исключение, перезаписи нет.

| Метод | Что делает |
|---|---|
| `get(k)` | значение или `null`; по `null` нельзя отличить «нет ключа» от «значение null» |
| `containsKey(k)` | только проверка наличия ключа |
| `putIfAbsent(k, v)` | кладёт `v`, только если ключа нет; возвращает старое значение или `null`; `v` вычисляется заранее |
| `computeIfAbsent(k, f)` | вызывает `f` только если ключа нет, кладёт результат и возвращает его; подходит, когда значение дорого создавать |

### Задание 4. Очередь ожидания
FIFO: первый пришёл, первый вышел. `ArrayDeque` быстрее `LinkedList` и не хранит лишних узлов.

| Бросает исключение | Возвращает спец. значение | Отличие |
|---|---|---|
| `add(e)` | `offer(e)` | в очереди с ограничением ёмкости `add` бросает `IllegalStateException`, `offer` возвращает `false` |
| `remove()` | `poll()` | на пустой очереди `remove` бросает `NoSuchElementException`, `poll` возвращает `null` |
| `element()` | `peek()` | то же: исключение против `null`, элемент не извлекается |

### Задание 5. Безопасное удаление при обходе
Enhanced for использует `Iterator`. Прямой `list.remove` меняет счётчик изменений списка, и следующий `next()` бросает `ConcurrentModificationException`.
Исправления: `iterator.remove()` или `removeIf(predicate)`.
Копирование всей коллекции перед обходом работает, но не всегда хорошо: это O(n) дополнительной памяти и времени на каждый вызов,
а копия может устареть, если коллекцию меняет кто-то ещё. `removeIf` проще и делает один проход.

### Задание 6. Result<T>
Ровно одно из двух: значение или ошибка (инвариант проверяют фабрики: `ok(null)` и пустая ошибка запрещены).
Две конкретизации: `Result<Integer>` и `Result<String>`. Защита на этапе компиляции, реальные ошибки компилятора:

```
String text = hours.get();            // incompatible types: Integer cannot be converted to String
Result<String> mixed = hours;         // incompatible types: Result<Integer> cannot be converted to Result<String>
```

### Задание 7. Generic-методы
`firstOrThrow` бросает `NoSuchElementException`, `swap` через `set` (при неверном индексе список не меняется, потому что `get` падает до первого `set`).
`indexBy` при повторе ключа бросает `IllegalStateException` с обоими элементами: тихо перезаписать или потерять значение нельзя.

### Задание 8. Ограничение типа
`<T extends Comparable<? super T>> T max(Collection<? extends T>)`. Вариант `T extends Comparable<T>` не подходит для `Dog extends Animal`:
`Dog` реализует `Comparable<Animal>`, а не `Comparable<Dog>`. `? super T` разрешает сравнивать через метод родителя.
`Collection<? extends T>` позволяет передать, например, `List<Dog>`.

### Задание 9. PECS (Producer Extends, Consumer Super)
`copy(List<? extends T> source, List<? super T> target)`: из `source` только читаем, в `target` только пишем.
Почему нельзя `add` в `List<? extends Course>`: это может быть `List<ЛюбойПодтипCourse>`, и компилятор не знает, какой именно.
Реальная ошибка: `incompatible types: Course cannot be converted to CAP#1`. Разрешён только `null`.
Из `List<? super Course>` читать можно только как `Object` (там может лежать любой надтип `Course`), зато добавлять `Course` можно.

### Задание 10. Контракт ключа
`equals/hashCode` только по `id`: смена `title` ничего не ломает, множество и карта продолжают находить элемент.
Если `title` входит в `hashCode`, после его изменения элемент лежит в старой корзине, а ищется по новому хэшу:
`contains` и `get` не находят его, `remove` не удаляет, повторный `add` создаёт дубликат, а обход всё ещё показывает старый элемент.
Вывод: поля, входящие в `equals/hashCode`, должны быть неизменяемыми, а ключ коллекции лучше брать из неизменяемых объектов.

### Задание 11. Выбор по нагрузке

| Сценарий | Интерфейс -> реализация | Главные операции | Цена |
|---|---|---|---|
| Каталог по ID | `Map` -> `HashMap` | `get`, `put` в среднем O(1) | порядка нет, память на таблицу и узлы |
| Отсортированный leaderboard | `NavigableSet` -> `TreeSet` (с `Comparator`) | `add`, `remove`, `first` — O(log n) | дороже `HashSet` по времени, красно-чёрное дерево |
| Очередь | `Queue`/`Deque` -> `ArrayDeque` | `offer`, `poll`, `peek` — O(1) | нет индексного доступа и `null` |
| Уникальные теги с порядком | `Set` -> `LinkedHashSet` | `add`, `contains` — O(1) | дополнительная двусвязная цепочка ради порядка добавления |
| Диапазонный поиск | `NavigableMap` -> `TreeMap` (`subMap`) | поиск и диапазон — O(log n + k) | O(log n) вместо O(1), зато упорядочено |
| Частый доступ по индексу | `List` -> `ArrayList` | `get(i)` — O(1), `add` в конец — амортизированно O(1) | вставка в середину O(n), запас ёмкости |

### Задание 12. Repository<ID, T>
Хранилище `LinkedHashMap` (порядок добавления, поиск по ID за O(1)). `null` не принимается нигде (`requireNonNull`).
`findAll` возвращает `List.copyOf`, то есть неизменяемый снимок: изменить внутреннюю коллекцию снаружи нельзя.
`findById` возвращает `Optional`.
Семантика повторного `save`: перезапись по ID (upsert), позиция в порядке сохраняется, метод возвращает сохранённый объект.
`deleteById` возвращает `true`, если что-то удалил.

### Задание 13. Обратный индекс
`Map<Tag, Set<CourseId>>` — основной индекс; `Map<CourseId, Set<Tag>>` нужна, чтобы при удалении курса не обходить все теги.
- `HashMap` для обеих карт: поиск по ключу O(1), порядок ключей не важен.
- `LinkedHashSet` для множеств курсов и тегов: быстрый `contains/remove` и детерминированный порядок вывода.
- Пересечение: первое множество копируется, остальные применяются через `retainAll` (исходный индекс не портится).
- После удаления курса пустое множество удаляется из индекса (`'streams'` и `'sql'` исчезли в примере).
- Повторное `add` того же курса сначала удаляет старые связи.

### Задание 14. LruCache<K, V>
`LinkedHashMap` с `accessOrder = true` хранит ключи от самого старого к самому новому: `get` и `put` перемещают ключ в конец.
`removeEldestEntry` удаляет самый старый элемент, когда размер превысил ёмкость.
Политика `null`: ключ и значение `null` запрещены (`NullPointerException`), поэтому `get` возвращает `Optional` и «нет ключа» однозначно отличимо от значения.
Промах (`get` несуществующего ключа) порядок не меняет. Повторный `put` существующего ключа обновляет значение и не вытесняет лишнего.
Стабильность ключей: ключ `record Key` равен другому экземпляру с теми же полями, поэтому кэш находит значение; изменяемые ключи использовать нельзя (см. задание 10).

### Задание 15. Планировщик prerequisites
`Map<T, Set<T>>`: вершина -> курсы, которые от неё зависят (`LinkedHashMap` + `LinkedHashSet`).
Порядок вставки сохраняется, поэтому одинаковый ввод всегда даёт одинаковый результат.
Порядок изучения находится алгоритмом Кана: очередь `ArrayDeque` из вершин без входящих зависимостей, счётчики входящих рёбер в `HashMap`.
Если обработаны не все вершины, значит есть цикл: DFS по тому же графу возвращает путь вида `B -> C -> D -> B`.
Сложность обоих алгоритмов O(V + E), память O(V + E).
Отсутствующая вершина: `dependentsOf` бросает `IllegalArgumentException` (`null` не возвращается, чтобы не прятать ошибку).
Пустой граф даёт пустой порядок, петля `X -> X` определяется как цикл.
